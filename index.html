Inside a scope document

  • In scope: IP ranges, domains/subdomains, web apps, APIs, mobile apps, cloud accounts, source/white-box access.
  • Out of scope: third-party SaaS, production data with live PII, partner-hosted infrastructure, physical sites, employee devices.
  • Window & load: testing dates and hours, rate limits, concurrent connections, blackout periods.
  • Prohibited: DoS/DDoS, destructive payloads, social engineering, physical intrusion, exfiltration beyond proof.
  • Contacts: technical POC, escalation path, emergency stop (“kill switch”), deconfliction with the client’s blue team.

Engagement models

Model Knowledge given Simulates Typical use
Black box None — external attacker view A real-world outsider External perimeter, web apps
Grey box Partial — a user or limited docs An insider or breached user Active Directory, internal, privesc
White box Full — source, design, credentials Maximum-coverage review Code review, deep application testing

Legal & governance

  • NDA — mutual, signed before any technical detail is exchanged.
  • Statement of Work — scope, timeline, deliverables, fees, limits of liability.
  • Rules of Engagement — exactly what, when and how may be tested, plus comms and the stop condition.
  • Authorisation letter — written proof the client authorised testing, with a 24/7 contact.
  • Insurance — professional indemnity and cyber liability.
  • Change control — how scope changes are approved mid-engagement.
  • Data handling — encrypted storage, access control, retention period, verifiable destruction.

Rules I set

  • Time-box each box (roughly 2–3 hours) to force efficient enumeration.
  • No hints until genuinely stuck; walkthroughs only after rooting.
  • Redo the machine unaided a week later to confirm it actually stuck.
  • Write up only what I can reproduce from scratch.

Progression

I rotate the target OS and category — Linux, Windows, Active Directory, web and cloud — and step Easy → Medium → Hard, so coverage stays balanced instead of grinding one topic.
